## 1. 文档目的

本文档定义一个强调隐私、公开侧匿名、支持多板块讨论的社区论坛。它用于统一产品、设计、前端、后端、测试、运维和内容治理的实现范围，并作为版本验收依据。

本文所称“匿名”不是无法被任何主体追踪的绝对匿名，而是：

1. 不要求用户提供手机号、邮箱、姓名、身份证、地理位置等直接身份信息。
2. 公开页面不展示可跨帖子追踪的固定用户身份。
3. 数据库只保存完成业务所必需的随机身份标识和内容数据。
4. IP、完整 User-Agent 等网络标识不进入业务数据库，不写入长期日志。
5. 浏览历史、头像、投票和已读位置以随机匿名账号关联，并允许用户查看、关闭同步和清除。

必须明确：只要要在不同设备间同步头像、投票、历史和已读位置，服务端就必须能把这些数据关联到同一个随机账号。因此本产品实现的是“假名化、数据最小化的匿名社区”，而不是数据库内部活动完全不可关联的密码学匿名系统。若要求连数据库运营者也无法关联同一人的活动，则云端历史、跨设备恢复、一人一票和持续头像无法同时成立。

## 2. 产品概述

### 2.1 产品定位

一个无需手机号或邮箱即可使用的匿名论坛。用户可进入“闲时吐槽”“技术分享”“热点八卦”等板块发帖、回帖、点赞、点踩、使用表情包和标签，并能在下次打开帖子时自动回到上次阅读的位置。管理员可配置论坛名称、Logo、板块、标签、公告和内容治理规则。

### 2.2 核心价值

- 降低表达门槛：无需注册实名资料，首次访问即可获得匿名身份。
- 降低身份压力：默认不在不同帖子间暴露稳定昵称或账号主页。
- 保持讨论秩序：楼层、楼主/层主标识、投票、举报和管理工具完整。
- 保持阅读连续性：自动保存浏览历史与已读进度，返回时直达断点。
- 保持品牌可配置：论坛名称、Logo、主题、公告、板块和标签均由管理员管理。

### 2.3 目标用户

- 希望低压力表达观点、情绪或经历的普通用户。
- 希望匿名交流技术、职业问题和经验的从业者。
- 希望围绕热点事件进行短期讨论的社区用户。
- 负责社区配置、内容审核、风险处置和运营的管理员。

### 2.4 成功指标

首发后以聚合指标衡量，不引入第三方跨站跟踪：

| 指标 | 定义!|MVP 目标 |
| --- | --- | --- |
| 发帖成功率 | 成功发布帖子数 / 发帖提交数 | ≥ 99% |
| 回帖成功率 | 成功发布回复数 / 回复提交数 | ≥ 99% |
| 阅读续接成功率 | 点击“继续阅读”后落到正确断点的次数 / 尝试次数 | ≥ 98% |
| 次日匿名身份保留率 | 次日仍持有有效本机匿名会话的设备比例 | 仅观察，建立基线 |
| 举报首次处理时长 | 举报创建至首次管理动作的中位数 | < 12 小时 |
| 核心页面性能 | 首页、板块页、帖子页 LCP P75 | < 2.5 秒 |
| 可用性 | 月度服务可用时间 | ≥ 99.9% |

聚合分析不得保存完整 IP、广告 ID、浏览器指纹或将用户行为发送给广告平台。

## 3. 产品原则与关键决策

### 3.1 产品原则

1. 隐私默认开启：数据最小化是默认值，不依赖用户手动关闭跟踪。
2. 公开身份弱关联：同一用户在不同帖子中的公开代号不同。
3. 线程内可辨识：同一用户在同一个帖子内使用稳定代号，保证讨论可读性。
4. 可撤回、可清理：历史、已读进度、上传头像和匿名身份支持自助清除。
5. 安全优先于“无痕”：必要的反滥用数据只能短期、不可逆、隔离保存。
6. 管理动作可审计：管理员的隐藏、删除、封禁、改配置等动作必须留审计记录。

### 3.2 默认产品决策

| 主题 | 决策 |
| --- | --- |
| 注册方式 | 首次访问自动创建随机匿名身份，不收集邮箱和手机号 |
| 会话恢复 | 默认本机 HttpOnly 会话；用户可主动生成一次性恢复短语，或绑定不含个人资料的 Passkey |
| 公开昵称 | 每个帖子内生成稳定的“匿名 A1/A2…”代号；跨帖子不可直接对照 |
| 楼主标识 | 发帖人在其帖子内显示“楼主”；其回帖同时带“楼主”徽标 |
| 层主标识 | 每个回复的作者是该楼层“层主”；被引用时显示“回复 N 楼层主” |
| 回复结构 | 主时间线保持楼层顺序；支持引用某楼层，不做无限嵌套评论树 |
| 投票 | 每个匿名身份对同一目标只能点赞或点踩一次，可取消或切换 |
| 浏览历史 | 默认保存到匿名账号；设置中可关闭云端同步并清空；本机模式只保存在浏览器 |
| 阅读进度 | 记录最高已读楼层和最近锚点；再次进入时提示一键跳转，不强制劫持滚动 |
| 删除策略 | 用户删除后公开内容立即变为占位符；短期安全留存后物理清除，合法合规冻结除外 |
| 内容格式 | MVP 使用受限 Markdown + 表情包，不允许任意 HTML |
| 图片 | 对象存储；上传时去除 EXIF、重编码、病毒检测、生成缩略图 |

## 4. 范围与版本规划

### 4.1 P0：MVP 必须交付

- 自动创建匿名身份、会话续期、退出并销毁本机身份。
- 同一代码库可在部署时选择 SQLite、PostgreSQL 或 MySQL，三种数据库通过同一套 P0 行为验收。
- 首页、板块列表、帖子列表、帖子详情。
- 发帖、编辑、删除、回帖、引用回复、楼层编号。
- 楼主与层主标识、线程内匿名代号。
- 点赞、点踩、取消和切换投票。
- 管理员管理板块、标签、论坛名称、Logo、Favicon、简介和主题色。
- 发帖标签、官方表情包、头像预设及自定义头像。
- 公告发布、定时展示、置顶、失效。
- 浏览历史、已读位置保存、继续阅读、清空和关闭同步。
- 搜索帖子标题与正文。
- 举报、内容隐藏、锁帖、删帖、匿名账号限制和管理审计。
- 响应式适配、基础 SEO、无障碍、性能和安全基线。

### 4.2 P1：首发后增强

- 草稿箱与本机自动保存。
- 帖子收藏。
- 热门榜、趋势标签、板块订阅。
- 回复提醒的站内收件箱；不依赖邮箱或手机推送。
- PWA 安装与离线阅读最近内容。
- 帖子投票/问卷。
- 管理员自定义表情包分组、敏感板块年龄提示。
- 数据导出包和更细粒度的隐私控制。

### 4.3 P2：远期能力

- 联邦化或多站点部署。
- 端到端加密的私密小组。
- Tor/I2P 镜像站。
- 密码学匿名凭证、零知识一人一票。
- 原生移动端应用。

### 4.4 明确不在 MVP 范围

- 私信、群聊、语音房、直播。
- 关注用户或公开粉丝关系。
- 广告画像、跨站分析、推荐算法画像。
- 实名认证、手机号/邮箱找回。
- 加密货币、积分交易和付费内容。
- 任意 HTML、可执行脚本或第三方 iframe 嵌入。

## 5. 角色与权限

### 5.1 角色定义

- 访客：未建立或已丢失匿名身份，可浏览公开内容和公告。
- 匿名用户：持有有效匿名会话，可发帖、回复、投票、举报、设置头像、保存历史。
- 板块管理员：管理指定板块中的帖子、回复和举报。
- 超级管理员：管理全站设置、板块、标签、表情包、管理员、审计和全站内容。
- 系统任务：执行定时公告、清理过期数据、内容扫描、索引同步等后台操作。

## 7. 核心用户流程

### 7.1 首次访问与匿名身份

1. 用户首次打开站点。
2. 服务端创建随机匿名账号和会话，不要求填写任何信息。
3. 服务端设置 `HttpOnly + Secure + SameSite=Lax` 的会话 Cookie。
4. 用户可立即浏览；执行发帖、回复、投票等写操作时确认社区规则。
5. 设置页提示：清除浏览器数据会丢失身份，可生成恢复短语或绑定 Passkey。
6. 恢复短语只在客户端显示一次；服务端仅保存慢哈希，不保存明文。

### 7.2 发帖

1. 用户在板块页选择“发布帖子”。
2. 系统校验会话状态、板块权限、频率限制和禁言状态。
3. 用户填写标题、正文，选择 0–5 个允许用于该板块的标签，可插入表情包和图片。
4. 客户端提供预览；提交时服务端再次校验、清理 Markdown 和媒体引用。
5. 内容通过同步安全检查后发布；命中高风险规则时进入待审或拒绝并给出申诉入口。
6. 发布成功后跳转帖子页，作者显示“楼主”。

### 7.3 回帖与楼层

1. 用户在底部回复，或点击某楼层“引用”。
2. 系统展示被引用楼层摘要，提交时保存被引用回复 ID。
3. 数据库事务为回复分配帖子内连续楼层号。
4. 回帖发布后定位到新楼层；作者是该楼“层主”。
5. 同一作者在该帖子内的公开匿名代号保持一致，跨帖子重新生成。

### 7.4 投票

1. 用户点击点赞或点踩。
2. 未投票时创建投票；点击相同按钮时取消；点击相反按钮时切换。
3. UI 乐观更新，服务端以数据库唯一约束保证一人一票。
4. 投票数以服务端结果回写，异常时撤销乐观状态。
5. 用户不能给自己发布的主帖或回复投票。

### 7.5 阅读续接

1. 用户阅读帖子时，客户端用 `IntersectionObserver` 计算当前最后完整看过的楼层。
2. 每 5 秒最多同步一次，并在页面隐藏、离开或关闭前尽力补发。
3. 服务端只保存最高已读楼层、最近锚点和更新时间，不保存逐次滚动轨迹。
4. 用户再次进入有新增回复的帖子时，页面显示“上次看到 N 楼，继续阅读”。
5. 用户点击后跳转到 N 楼附近，并将第一个未读楼层高亮 2 秒。
6. 如果原锚点被删除，回退到最近仍存在的前一楼层；若无新增回复则恢复最近锚点。

### 7.6 销毁匿名身份

1. 用户进入隐私设置并选择“销毁匿名身份”。
2. 页面明确提示后果：会话、历史、投票归属和恢复能力将丢失。
3. 用户进行二次确认。
4. 系统撤销全部会话，排队删除头像、浏览历史和恢复凭证；公开内容按社区删除政策处理。
5. 当前设备 Cookie 被清除，后续访问获得全新随机身份。

## 8. 功能需求与验收标准

优先级定义：P0 为 MVP 阻断项；P1 为首发后优先；P2 为远期。

### 8.1 匿名身份与会话

#### ANON-001 自动匿名身份（P0）

需求：首次访问自动获得随机匿名身份，用户不填写任何个人资料。

验收标准：

- 首次请求后可获得有效会话，流程中不出现邮箱、手机号、姓名输入项。
- 匿名账号 ID 使用不可枚举随机 ID，不以 IP、设备信息或时间戳直接生成。
- Cookie 不包含明文账号 ID，只包含高熵会话令牌；数据库只保存令牌哈希。
- 会话令牌轮换、撤销和过期策略生效。

#### ANON-002 身份恢复（P0）

需求：用户可选择恢复短语或 Passkey，以便更换设备后恢复匿名身份。

验收标准：

- 未启用恢复方式不影响正常使用。
- 恢复短语明文只显示一次，服务端不可还原。
- 连续恢复失败触发指数退避和短期速率限制。
- 恢复成功后旧会话可由用户选择全部撤销。

#### ANON-003 线程内匿名代号（P0）

需求：公开身份在同一帖子内可识别、跨帖子不可直接关联。

验收标准：

- 同一账号在同一帖子内始终显示相同代号。
- 同一账号在不同帖子内的代号不同。
- 楼主固定显示“楼主”；楼主回帖带“楼主”徽标。
- 页面源代码和公开 API 不返回内部账号 ID。

#### ANON-004 会话与设备管理（P1）

需求：用户可查看匿名会话的粗略创建时间、最近使用时间，并撤销其他会话。

验收标准：不得展示或保存精确地理位置、完整 IP、完整 User-Agent；设备名称由用户自定义或使用粗粒度类别，如“移动设备”。

### 8.2 品牌与站点设置

#### SITE-001 品牌配置（P0）

管理员可配置：

- 论坛名称、短名称、简介、页脚文本。
- 浅色/深色 Logo、Favicon、默认分享图。
- 主色、强调色、默认色彩模式。
- 默认语言、时区、每页数量。
- SEO 标题模板、描述、是否允许搜索引擎索引。

验收标准：

- 保存后新请求立即生效，已打开页面在刷新后生效。
- Logo/Favicon 上传校验格式、尺寸和文件大小，并生成安全变体。
- 管理设置有版本记录，可回滚到最近 20 个版本。
- 错误配置不会导致站点无法访问，系统回退到默认品牌。

#### SITE-002 运营开关（P0）

管理员可控制全站只读、暂停新身份、暂停发帖/回帖、维护提示、默认内容排序和敏感内容策略。紧急开关变更必须记审计日志。

### 8.3 板块

#### BOARD-001 板块管理（P0）

字段包括：名称、Slug、图标、简介、板块规则、主题色、排序、可见性、是否只读、是否归档、默认标签、SEO 设置。

验收标准：

- Slug 全站唯一，创建后可修改并保留旧地址重定向。
- 隐藏板块不出现在导航或搜索结果；管理员仍可访问。
- 只读板块保留浏览但禁止普通用户发帖和回帖。
- 归档板块不接受新内容，已有 URL 保持可访问。

#### BOARD-002 默认板块（P0）

初始化提供但允许管理员改名或删除：

- 闲时吐槽：生活、情绪和轻讨论。
- 技术分享：开发、产品、设计和工具经验。
- 热点八卦：公开热点、娱乐和社会话题。

删除非空板块前必须迁移内容或归档，不允许直接级联删除内容。

### 8.4 帖子

#### POST-001 创建帖子（P0）

| 字段 | 规则 |
| --- | --- |
| 板块 | 必填，且用户具有发帖权限 |
| 标题 | 4–120 个 Unicode 字符，去除首尾空白 |
| 正文 | 1–20,000 个字符，使用受限 Markdown |
| 标签 | 0–5 个，只能选择启用且适用于板块的标签 |
| 图片 | 单张 ≤ 10 MB，单帖最多 9 张，格式限 JPEG/PNG/WebP/GIF |
| 内容提示 | 可选：一般、剧透、敏感内容 |

验收标准：

- 客户端和服务端使用同一套可共享规则，但以服务端校验为准。
- 重复点击提交不会产生重复帖子，写接口支持幂等键。
- 任意 HTML、脚本、危险 URL 协议被移除。
- 图片在公开前已去除 EXIF 并通过文件类型真实性检测。

#### POST-002 展示帖子（P0）

帖子页包含标题、板块、标签、楼主标识、发布时间、编辑标记、正文、媒体、投票、分享、举报、楼层列表和回复框。

验收标准：

- 分享链接不包含匿名身份或追踪参数。
- 被锁帖子仍可浏览但不能新增回复。
- 被隐藏内容对普通用户显示统一占位状态，不泄露审核细节。
- 帖子总楼层数和投票数允许短暂最终一致，但刷新后必须正确。

#### POST-003 编辑与删除（P0）

- 作者发布后 30 分钟内可编辑标题、正文和标签；管理员不受该时限限制。
- 编辑后显示“已编辑”，并保存仅管理员可见的有限版本记录。
- 作者可随时请求删除自己的内容；主帖有回复时显示“原帖已删除”占位并保留楼层讨论。
- 无回复主帖可从公开列表移除。
- 管理员删除必须选择原因并写审计日志。

#### POST-004 列表、排序和筛选（P0）

- 排序：最新发布、最近回复、热门。
- 筛选：板块、标签、发布时间、是否有未读回复。
- 热门分数考虑净赞、回复数、时间衰减和举报/隐藏状态，不使用用户画像。
- 置顶帖优先于普通排序；全局置顶与板块置顶视觉上有区别。

### 8.5 回复与楼层

#### REPLY-001 发布回复（P0）

- 正文长度 1–10,000 字符，可插入受限 Markdown、表情包和最多 4 张图片。
- 支持引用一个已有楼层；引用快照最多显示 120 字并链接原楼层。
- 回复发布时在数据库事务内分配连续楼层号，首帖视为 1 楼或单独 OP 区域；本产品默认首个回复为 2 楼，主帖为 1 楼。
- 并发回复不得出现重复楼层号。

#### REPLY-002 层主与引用（P0）

- 每层展示“N 楼”“层主”“匿名 Ax”以及必要状态。
- 楼主发布的楼层展示“楼主”而不是普通匿名代号，但仍保留“层主”语义。
- 引用被删楼层时显示“引用内容已删除”，链接不报错。
- 不允许无限嵌套；所有新回复都进入主楼层时间线。

#### REPLY-003 编辑与删除（P0）

规则与帖子类似：作者 30 分钟内可编辑；删除后保留楼层占位和编号，其他楼层不重排。

### 8.6 点赞与点踩

#### VOTE-001 投票状态机（P0）

状态为：`none`、`up`、`down`。

| 当前状态 | 点击赞 | 点击踩 |
| --- | --- | --- |
| none | up | down |
| up | none | down |
| down | up | none |

验收标准：

- 同一匿名账号对同一帖子或回复最多一条有效投票。
- 用户不能投票自己的内容。
- 前端乐观更新失败后恢复服务端状态并展示轻提示。
- 被删除或隐藏的内容不能新增投票。
- API 返回赞数、踩数、净分和当前用户状态；公开列表默认只展示净分或由管理员配置。

### 8.7 标签

#### TAG-001 标签管理（P0）

管理员可新建、编辑、禁用、合并标签，并配置名称、Slug、颜色、描述、适用板块和排序。标签名称全站唯一；禁用后旧帖仍展示但新帖不可选择；合并后旧 URL 永久重定向。

#### TAG-002 帖子标签（P0）

发帖人可选择 0–5 个标签；发帖后的可编辑时限内可修改。标签页展示相关公开帖子，不返回隐藏、待审或已删除内容。

### 8.8 头像与匿名形象

#### AVATAR-001 头像设置（P0）

- 提供至少 24 个内置头像和自定义上传。
- 自定义头像 ≤ 5 MB，支持 JPEG/PNG/WebP，裁剪为正方形并生成 64/128/256 像素变体。
- 去除 EXIF、重编码并拒绝伪装文件。
- 用户可恢复默认随机头像或删除上传内容。

隐私展示规则：头像默认只在设置页和“我的历史”中展示；公开讨论区默认使用由帖子 ID 与匿名账号 ID 派生的线程内图案头像，避免用户通过自定义头像跨帖子被识别。管理员可允许用户选择“在所有帖子展示自定义头像”，但界面必须提示这会降低匿名性。

### 8.9 表情包

#### EMOJI-001 表情包使用（P0）

- 编辑器按分组展示官方表情包，支持搜索和最近使用。
- 正文中保存稳定短码或资源 ID，不保存可变 CDN 完整地址。
- 下架表情在历史内容中显示静态占位或保留审核后的冻结副本。
- GIF 自动播放遵循用户的“减少动态效果”系统设置。

#### EMOJI-002 表情包管理（P0）

管理员可上传、分组、命名、排序、替换和下架；系统校验版权确认、文件格式、尺寸、大小、恶意载荷和重复短码。

### 8.10 公告

#### NOTICE-001 公告管理与展示（P0）

公告字段：标题、正文、级别、作用范围、优先级、开始时间、结束时间、是否可关闭、链接和状态。

作用范围：全站、指定板块、仅管理后台。级别：信息、提醒、警告、紧急。

验收标准：

- 未到开始时间和已过结束时间的公告不在用户端展示。
- 紧急公告固定显示，不允许普通用户永久关闭。
- 可关闭公告的关闭状态只保存在匿名账号或本机，不泄露到公开 API。
- 公告正文经过与帖子相同的安全清理。

### 8.11 浏览历史与已读位置

#### HISTORY-001 浏览历史（P0）

- 用户进入帖子并停留超过 3 秒或产生有效阅读后记录历史。
- 每个帖子只保留一条最新历史记录，不保存每次访问明细。
- 历史页按最近查看排序，展示标题、板块、最后查看时间、已读/总楼层和未读数量。
- 支持继续阅读、单条删除、全部清空。
- 用户关闭云端历史后，服务端停止新增/更新；可选择仅保存在本机。

#### HISTORY-002 自动定位（P0）

保存字段：最高已读楼层号、最近锚点楼层 ID、锚点内偏移可选值、最后查看时间。

验收标准：

- 有未读内容时默认显示非阻塞提示“从 N 楼继续”，用户点击后跳转。
- 设置中可开启“进入时自动跳转”；默认关闭，以避免页面突然滚动。
- 跳转后目标楼层顶部不能被吸顶导航遮挡。
- 楼层被删、分页变化或新回复并发到达时仍能落到最接近的有效位置。
- 多设备同步采用单调合并：最高已读楼层只增加；最近锚点按最后更新时间决定。
- 写入使用防抖和批量更新，页面滚动不会逐像素上报。

#### HISTORY-003 隐私控制（P0）

- 设置页明确说明历史与匿名账号关联。
- 关闭同步后，服务端在 24 小时内删除既有历史，除非用户选择保留。
- 清空后所有设备不可再恢复已清数据。
- 不把历史用于广告画像或跨站推荐。

### 8.12 搜索

#### SEARCH-001 内容搜索（P0）

- 搜索标题和正文，支持板块、标签、发布时间和排序过滤。
- 中文支持基本分词；搜索结果高亮匹配摘要。
- 隐藏、待审、删除和无权限内容不得出现在结果或数量统计中。
- 搜索词只以短期聚合形式统计，不与匿名账号关联；原始查询日志最多保留 7 天且不含 IP。

### 8.13 举报与治理

#### MOD-001 举报（P0）

举报原因：垃圾广告、骚扰攻击、隐私泄露、违法风险、血腥色情、错误板块、其他。用户可补充 500 字说明，同一账号不能重复举报同一目标。

#### MOD-002 管理动作（P0）

管理员可：忽略举报、内容警告、隐藏、取消隐藏、锁定、解锁、移动板块、移除标签、删除内容、限制账号发言、撤销会话。

验收标准：

- 每次动作必须包含标准原因；高风险动作可填写备注。
- 审计记录包含管理员 ID、对象、动作、前后状态、原因和时间。
- 批量操作需要二次确认并限制每次数量。
- 板块管理员不能处理范围外内容或提升自身权限。

#### MOD-003 反滥用（P0）

- 按匿名账号、短期网络令牌和全站压力实行分层限流。
- 网络令牌由边缘层使用每日轮换密钥对规范化 IP 做 HMAC，原始 IP 不持久化，令牌最长保留 24 小时。
- 新身份采用更严格的发帖/图片/链接额度；正常使用后逐步放宽。
- CAPTCHA 只在风险升高时触发，避免默认跟踪型验证码；优先使用隐私友好的挑战。
- 内容规则命中时支持拒绝、待审、降速三种动作，不直接向攻击者暴露具体规则。

### 8.14 用户自助数据管理

#### PRIVACY-001 查看与导出（P1）

用户可查看服务端持有的数据类别并生成机器可读导出包，包括自己的内容、投票、历史、设置和会话元数据。导出链接短期有效且只允许当前已验证会话访问。

#### PRIVACY-002 删除与身份销毁（P0）

用户可删除头像、历史、单条内容或整个匿名身份。身份销毁在 24 小时内完成在线数据清除；备份按既定周期自然过期，不重新注入在线系统。

## 9. 状态与业务规则

### 9.1 帖子状态

`pending`（待审）→ `published`（已发布）→ `locked`（锁定）/ `hidden`（隐藏）/ `deleted`（删除）/ `archived`（归档）。

- `pending` 仅作者和管理员可见。
- `locked` 可读但不可回复。
- `hidden` 对普通用户返回统一占位或 404，策略由隐藏原因决定。
- `deleted` 保留不可逆化占位及必要引用关系，正文进入清理队列。
- `archived` 只读并保留搜索策略配置。

### 9.2 回复状态

`pending` → `published` → `hidden` / `deleted`。回复删除不重排楼层号。

### 9.3 匿名账号状态

`active`、`read_only`、`muted_until`、`suspended`、`deletion_pending`、`deleted`。

### 9.4 时间规则

- 用户端显示相对时间并可查看绝对时间。
- 数据库存 UTC；展示按站点默认时区或用户本机时区。
- 公告和限制到期由后台任务与请求时校验双重保证。

### 9.5 计数规则

- 赞、踩、回复和浏览计数允许缓存带来秒级延迟。
- 安全和权限判断不得依赖缓存中的旧状态。
- 浏览量按匿名账号/本机的时间窗口去重，不追求跨网络精准去重。

## 10. 数据模型

数据库必须支持 SQLite、PostgreSQL、MySQL，并在部署时通过配置选择一种；不支持同一实例运行过程中热切换，也不要求一个站点同时写入多种数据库。所有主键由应用层生成 UUIDv7、ULID 或等价的高熵不可枚举字符串 ID，避免依赖特定数据库的自增或 UUID 扩展；公开 URL 使用独立 `public_id`，不得暴露内部匿名账号 ID。

### 10.1 核心实体

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `anonymous_users` | `id`, `status`, `avatar_asset_id`, `created_at`, `deletion_requested_at` | 随机匿名账号；无邮箱、手机、姓名、IP |
| `anon_sessions` | `id`, `user_id`, `token_hash`, `expires_at`, `last_used_at`, `revoked_at` | 仅存会话令牌哈希 |
| `recovery_credentials` | `id`, `user_id`, `type`, `secret_hash/public_key`, `created_at` | 恢复短语哈希或 Passkey 公钥 |
| `admin_users` | `id`, `username`, `credential_hash/public_key`, `role`, `status` | 与匿名用户分离，强制 MFA/Passkey |
| `boards` | `id`, `slug`, `name`, `description`, `rules`, `status`, `sort_order` | 板块配置 |
| `posts` | `id`, `public_id`, `board_id`, `author_id`, `title`, `body`, `status`, `next_floor_no`, timestamps | 主帖；`author_id` 永不进入公开响应 |
| `replies` | `id`, `public_id`, `post_id`, `author_id`, `floor_no`, `body`, `quote_reply_id`, `status`, timestamps | 楼层；唯一约束 `(post_id, floor_no)` |
| `thread_aliases` | `post_id`, `user_id`, `alias_index`, `avatar_seed` | 帖内匿名代号；唯一约束 `(post_id, user_id)` |
| `tags` | `id`, `slug`, `name`, `color`, `status` | 标签定义 |
| `board_tags` | `board_id`, `tag_id`, `sort_order` | 板块可用标签 |
| `post_tags` | `post_id`, `tag_id` | 帖子标签，多对多 |
| `votes` | `user_id`, `target_type`, `target_id`, `value`, `updated_at` | `value` 为 1/-1；目标联合唯一 |
| `announcements` | `id`, `scope`, `board_id`, `level`, `title`, `body`, `starts_at`, `ends_at`, `status` | 公告 |
| `announcement_dismissals` | `announcement_id`, `user_id`, `dismissed_at` | 可关闭公告状态 |
| `browsing_history` | `user_id`, `post_id`, `max_read_floor`, `anchor_reply_id`, `last_viewed_at` | 每用户每帖一条，不存逐次轨迹 |
| `emojis` | `id`, `group_id`, `shortcode`, `asset_id`, `status`, `sort_order` | 表情包 |
| `media_assets` | `id`, `owner_user_id`, `storage_key`, `mime`, `width`, `height`, `status` | 不保留原始文件名和 EXIF |
| `reports` | `id`, `reporter_id`, `target_type`, `target_id`, `reason`, `details`, `status` | 举报 |
| `moderation_actions` | `id`, `admin_id`, `action`, `target_type`, `target_id`, `reason`, `before`, `after`, `created_at` | 管理审计 |
| `site_settings_versions` | `id`, `version`, `settings_json`, `created_by`, `created_at` | 站点设置版本 |

### 10.2 关键索引与约束

- `boards(slug)` 唯一。
- `posts(public_id)`、`replies(public_id)` 唯一。
- `replies(post_id, floor_no)` 唯一并按楼层查询建组合索引。
- `votes(user_id, target_type, target_id)` 唯一。
- `browsing_history(user_id, post_id)` 唯一。
- `thread_aliases(post_id, user_id)` 唯一，`(post_id, alias_index)` 唯一。
- 帖子列表索引：`posts(board_id, status, last_replied_at desc)`。
- 搜索通过统一 `SearchRepository` 抽象：SQLite 可使用 FTS5，PostgreSQL 可使用全文检索，MySQL 可使用 FULLTEXT；若运行环境不具备对应扩展，则回退到可移植的规范化文本查询。中文搜索质量或数据规模提高后，应使用独立搜索服务，业务逻辑不得直接依赖某一种数据库的全文检索语法。
- 所有外键明确 `ON DELETE` 行为，禁止意外级联删除整帖讨论。

### 10.3 线程匿名代号生成

推荐方案：首次在帖子中出现时，在事务内分配顺序代号 `A1`、`A2`……并保存到 `thread_aliases`。公开 API 只返回代号和线程头像种子。

不直接展示由用户 ID 可逆或可离线穷举的哈希。若通过 HMAC 派生，必须使用服务端密钥和帖子作用域，且定期密钥轮换不能破坏历史代号。

### 10.4 数据保留

| 数据 | 默认保留 | 说明 |
| --- | --- | --- |
| 已发布内容 | 至用户删除或管理员处置 | 社区公开内容 |
| 浏览历史/阅读进度 | 最近 180 天滚动保留 | 用户可随时清空或关闭 |
| 撤销会话 | 30 天 | 仅哈希和撤销状态 |
| 原始上传文件 | 处理成功即删除 | 只保留去元数据后的安全变体 |
| 短期网络 HMAC 令牌 | ≤ 24 小时 | 存 Redis 类隔离存储，不进业务 DB |
| 应用访问日志 | 7–14 天 | 不含 Cookie、正文、查询词、原始 IP |
| 管理审计 | 1 年 | 不包含终端用户 IP |
| 在线软删除正文 | 7–30 天 | 具体周期由部署地区法规配置 |
| 加密备份 | ≤ 35 天 | 到期销毁密钥/备份，不恢复已删除数据到线上 |

### 10.5 数据库兼容规范

#### 10.5.1 部署选择

使用环境变量在部署时确定数据库类型：

```text
DATABASE_DRIVER=sqlite | postgres | mysql
DATABASE_URL=<对应数据库连接地址>
```

- SQLite：适合本地开发、演示、个人站点和单实例低流量部署。
- PostgreSQL：推荐用于公共生产站点和高并发部署。
- MySQL：适合已有 MySQL 基础设施的生产部署，最低能力要求为支持事务、行锁、外键和 `utf8mb4`。
- 从一种数据库切换到另一种数据库属于离线迁移操作，必须使用经过验证的导出、转换、导入和校验工具，不能只修改环境变量。

#### 10.5.2 可移植字段约束

- ID 在应用层生成，数据库列统一映射为定长或变长字符串；不得依赖 PostgreSQL UUID 扩展或数据库自增 ID 作为公开标识。
- 枚举在应用层校验并以短字符串存储，迁移不得依赖某一数据库独有的枚举类型。
- 站点设置和审计快照以 JSON 字符串保存，由 Zod 做结构校验；可使用原生 JSON 类型优化，但不得把核心查询建立在单一数据库的 JSON 运算符上。
- 时间统一按 UTC 写入并由数据访问层规范化精度；业务逻辑不得依赖数据库本地时区。
- 正文、标题、标签和 Slug 使用 Unicode；MySQL 必须使用 `utf8mb4`，唯一键比较规则必须经过大小写和 Unicode 一致性测试。
- 布尔值、时间、JSON 和大文本只通过数据访问层读写，不在领域服务中假定底层物理类型。
- 不使用数组列、部分索引、存储过程、触发器、生成列等非通用能力实现核心业务；标签等集合关系使用关联表。

#### 10.5.3 事务与并发

- PostgreSQL/MySQL 为帖子行加锁并原子更新 `next_floor_no`，在同一事务中插入回复。
- SQLite 开启 WAL、设置合理的 busy timeout，并使用 `BEGIN IMMEDIATE` 或等价写事务完成楼层分配；遇到锁冲突进行有上限的随机退避重试。
- 三种数据库都必须保留 `(post_id, floor_no)`、投票目标、浏览历史等唯一约束，应用层重试不能替代数据库约束。
- 服务层统一处理死锁、序列化失败、SQLite busy 和唯一键冲突，将其映射为可重试错误或幂等成功。
- SQLite 模式限制为单区域、少量应用实例；当写锁等待、队列积压或并发写入超过阈值时，运维界面提示迁移至 PostgreSQL/MySQL。

#### 10.5.4 Schema 与迁移

- 领域模型保持一致，每个数据库方言维护可审查、可回滚的迁移产物。
- CI 必须分别在 SQLite、PostgreSQL、MySQL 上从空库执行全部迁移，并从上一发布版本执行升级迁移。
- 迁移命令必须显式读取 `DATABASE_DRIVER`，禁止把 SQLite 迁移误用到生产 PostgreSQL/MySQL。
- 每个发布版本维护三种数据库的 schema checksum；启动时发现驱动、迁移历史或 schema 不匹配应拒绝写入并给出明确运维错误。
- 跨数据库导入工具必须校验表行数、内容状态计数、楼层唯一性、投票聚合、媒体引用和随机抽样哈希。

#### 10.5.5 能力矩阵

| 能力 | SQLite | PostgreSQL | MySQL |
| --- | --- | --- | --- |
| 推荐场景 | 本地/个人/低流量 | 公共生产首选 | 公共生产/既有基础设施 |
| 多实例并发写 | 有限，不推荐 | 支持 | 支持 |
| 楼层分配 | WAL + 即时写事务 | 行锁事务 | InnoDB 行锁事务 |
| 全文搜索 | FTS5，可选 | 原生全文检索 | FULLTEXT |
| JSON 优化 | JSON1，可选 | JSON/JSONB | JSON |
| 备份 | 在线备份 API/文件快照 + WAL | 逻辑备份/PITR | 逻辑备份/binlog PITR |
| MVP 自动化测试 | 必须 | 必须 | 必须 |

三种数据库对用户提供相同的 P0 功能和 API 语义。数据库特有优化只能影响性能，不得改变匿名性、权限、楼层、投票、删除或阅读进度规则。

## 11. API 设计

API 使用 `/api/v1` 前缀。用户端读接口可由 Next.js Server Components 直接调用领域服务；对客户端交互暴露 Route Handlers。写操作必须鉴权、CSRF 防护、服务端校验、限流和幂等处理。

### 11.1 匿名会话

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/v1/anon/session` | 创建或刷新匿名会话 |
| `DELETE` | `/api/v1/anon/session` | 退出当前设备 |
| `GET` | `/api/v1/anon/sessions` | 查看当前匿名身份会话 |
| `DELETE` | `/api/v1/anon/sessions/:id` | 撤销指定会话 |
| `POST` | `/api/v1/anon/recovery` | 创建恢复方式 |
| `POST` | `/api/v1/anon/recover` | 恢复匿名身份 |
| `DELETE` | `/api/v1/anon/identity` | 销毁匿名身份 |

### 11.2 板块、帖子和回复

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/boards` | 板块列表 |
| `GET` | `/api/v1/boards/:slug/posts` | 板块帖子列表 |
| `POST` | `/api/v1/posts` | 创建帖子 |
| `GET` | `/api/v1/posts/:publicId` | 帖子详情与第一页楼层 |
| `PATCH` | `/api/v1/posts/:publicId` | 编辑自己的帖子 |
| `DELETE` | `/api/v1/posts/:publicId` | 删除自己的帖子 |
| `GET` | `/api/v1/posts/:publicId/replies` | 游标分页读取楼层 |
| `POST` | `/api/v1/posts/:publicId/replies` | 发布回复 |
| `PATCH` | `/api/v1/replies/:publicId` | 编辑自己的回复 |
| `DELETE` | `/api/v1/replies/:publicId` | 删除自己的回复 |

### 11.3 投票、历史和媒体

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `PUT` | `/api/v1/votes/:targetType/:publicId` | 设置 `up/down/none` |
| `GET` | `/api/v1/history` | 浏览历史 |
| `PUT` | `/api/v1/history/:postPublicId` | 合并已读位置 |
| `DELETE` | `/api/v1/history/:postPublicId` | 删除单条历史 |
| `DELETE` | `/api/v1/history` | 清空历史 |
| `POST` | `/api/v1/media/upload-intents` | 获取受限上传凭证 |
| `POST` | `/api/v1/media/:id/complete` | 确认上传并进入处理队列 |
| `POST` | `/api/v1/reports` | 举报内容 |

### 11.4 管理 API

管理 API 位于 `/api/v1/admin/*`，包括站点设置、板块、标签、表情、公告、内容、举报、账号限制和审计。所有写操作必须附带操作原因；高危操作要求近期二次认证。

### 11.5 响应约定

```json
{
  "data": {},
  "error": null,
  "meta": {
    "requestId": "random-request-id"
  }
}
```

错误只返回稳定错误码和对用户安全的提示，不返回数据库结构、堆栈、内部账号 ID、风控阈值或敏感策略细节。分页默认使用不透明游标，不使用可枚举偏移作为唯一方案。

## 12. Next.js 技术方案

### 12.1 推荐栈

| 层 | 选择 | 说明 |
| --- | --- | --- |
| Web 框架 | Next.js App Router + TypeScript | Server Components 优先，交互区域使用 Client Components |
| 样式与组件 | Tailwind CSS + 可访问性组件层 | 建立站点 Token，避免业务页散落硬编码样式 |
| 表单与校验 | React Hook Form + Zod | 前后端共享 schema，服务端为最终可信边界 |
| 数据库 | SQLite / PostgreSQL / MySQL | 部署时选择；公共生产默认推荐 PostgreSQL |
| 数据访问 | Dialect Adapter + ORM（默认推荐 Prisma） | 为三种方言维护独立迁移，领域服务不直接写方言 SQL |
| 缓存/限流 | Redis 兼容服务 | 热门列表、聚合计数、短期网络令牌、任务锁 |
| 对象存储 | S3 兼容私有桶 + CDN | 通过处理流水线生成公开安全变体 |
| 后台任务 | 独立 Worker/队列 | 媒体处理、清理、公告定时、搜索索引 |
| 监控 | OpenTelemetry + 自托管/受控监控 | 采集性能和错误，主动剔除用户内容与标识 |
| 测试 | Vitest、Testing Library、Playwright | 单元、组件、API、E2E 和无障碍测试 |

依赖版本由项目 lockfile 固定，并使用仍受维护的稳定版本；不得在 PRD 中把浮动的 `latest` 当作可复现构建依据。

### 12.2 应用分层

```text
Browser
  ├─ Server-rendered pages / React Server Components
  └─ Client interactions: editor, voting, read progress
          │
Next.js Route Handlers / Server Actions
          │
Domain services: identity, forum, vote, history, moderation
          │
Repository + database dialect adapter
          ├──────── SQLite
          ├──────── PostgreSQL
          ├──────── MySQL
          ├──────── Redis-compatible cache / rate limit
          ├──────── Object storage / media worker
          └──────── Search index (optional after MVP)
```

### 12.4 渲染与缓存

- 论坛首页、板块页和公开帖子主体优先服务端渲染，兼顾首屏和 SEO。
- 个性化内容如投票状态、历史断点由请求级鉴权读取，禁止进入共享缓存。
- 公共帖子内容与匿名个性化数据分离，避免 CDN 缓存泄露 Cookie 关联响应。
- 站点设置使用带版本号的缓存键；管理员修改后主动失效。
- 写入后对相关路径或缓存标签执行精确失效，不全站清缓存。
- 帖子回复使用游标分页；长帖可虚拟化，但锚点定位必须兼容未加载楼层。

### 12.5 已读位置实现

- 每个楼层 DOM 使用稳定 `id="floor-{publicId}"` 和 `data-floor-no`。
- `IntersectionObserver` 只标记完整或超过阈值可见的楼层。
- 客户端本地维护候选最大楼层，通过 5 秒防抖写入。
- API 执行 `max(existing.max_read_floor, incoming.max_read_floor)`，避免旧设备覆盖新进度。
- 自动跳转前先按楼层号请求包含锚点的分页游标，再使用 `scrollIntoView` 和 CSS `scroll-margin-top`。
- 对 Safari 页面冻结、移动端后台等场景监听 `visibilitychange`，但不依赖不可靠的 `beforeunload` 作为唯一保存方式。

## 13. 隐私、安全与威胁模型

### 13.1 数据库中禁止存储

- 手机号、邮箱、姓名、身份证号、通讯录。
- 原始 IP、精确地理位置、长期网络标识。
- 完整 User-Agent、Canvas/WebGL/字体等浏览器指纹。
- 原始图片 EXIF、GPS、设备序列信息和原始文件名。
- 恢复短语明文、会话令牌明文、管理员密码明文。
- 第三方广告 ID、社交平台账号映射。

用户自行发布的正文可能包含个人信息，系统无法保证内容天然匿名。编辑器必须持续提示“请勿发布姓名、联系方式、住址、工号、可识别照片等信息”，并提供隐私泄露举报的最高优先级通道。

### 13.2 威胁边界

| 威胁主体 | 防护目标 | 已知边界 |
| --- | --- | --- |
| 普通访客 | 无法从公开页面关联跨帖身份 | 重复文风、自定义头像或自曝信息仍可能关联 |
| 数据库泄露者 | 无直接身份字段、无明文会话令牌、无原始 IP | 可看到同一随机账号关联的活动，属于假名化而非不可关联 |
| 恶意第三方脚本 | 不获得会话和行为数据 | 严格 CSP，尽量不加载第三方脚本 |
| 网络服务提供者/CDN | 减少长期终端识别 | 网络层天然可见连接元数据，需合同、日志和边缘配置约束 |
| 管理员 | 权限最小化、动作可审计 | 授权管理员仍可看到内部随机账号的违规关联记录 |
| 终端入侵者 | 会话令牌不可被 JS 直接读取 | 已解锁设备、浏览器配置和截图不在服务端可控范围内 |

### 13.3 应用安全要求

- 全站 HTTPS、HSTS、Secure/HttpOnly/SameSite Cookie。
- 状态变更请求采用 CSRF Token 或严格 Origin 校验；关键操作二次验证。
- CSP 默认拒绝，脚本使用 nonce/hash；禁用不必要的第三方脚本。
- Markdown 使用允许列表清理；链接添加安全属性，禁止 `javascript:` 等协议。
- 所有查询参数化；ORM 逃生 SQL 必须代码审查。
- IDOR 防护：每个写操作在服务端校验资源所有权和角色范围。
- 上传经 MIME 魔数验证、大小/像素限制、病毒检测、解码重编码和隔离桶处理。
- 会话令牌至少 256 位随机熵，数据库保存强哈希；发生提权或恢复时轮换。
- 管理后台强制 Passkey 或 MFA，敏感动作需近期认证。
- 密钥使用托管 KMS，生产密钥不得进入仓库、构建日志或客户端包。
- 数据库和备份加密，生产数据库禁止公共网络访问。
- 定期依赖审计、SAST、秘密扫描和渗透测试。

### 13.4 日志与可观测性

- 应用日志不记录 Cookie、Authorization、正文、回复、搜索词、恢复短语、上传文件名。
- 请求 ID 随机生成，不从匿名账号 ID 派生。
- 错误监控在客户端发送前清理 URL 查询参数和用户输入。
- 性能指标只保留路由模板，如 `/t/[id]`，不保留真实标题或完整 URL。
- 运维访问生产数据必须按角色授权、限时、审批并审计。

### 13.5 隐私模式

提供两个清晰模式：

| 模式 | 服务端历史 | 跨设备恢复 | 投票/发帖 | 适用场景 |
| --- | --- | --- | --- | --- |
| 标准匿名模式 | 保存最小化历史和断点 | 可选 | 支持 | 默认，功能完整 |
| 仅本机历史模式 | 不保存历史/断点 | 身份仍可选恢复 | 支持 | 不希望云端保存阅读记录 |

“完全无服务端身份”不作为 MVP 模式，因为它无法可靠支持投票去重、内容归属和滥用处置。可在远期用匿名凭证研究解决。

## 14. 内容治理与社区规范

### 14.1 基本规则

禁止发布：

- 他人的个人身份、联系方式、住址、精确位置、账号凭证等隐私信息。
- 明确违法内容、交易或操作指引。
- 针对个人或群体的威胁、持续骚扰、仇恨攻击。
- 未经同意的私密影像、性剥削内容和未成年人不当内容。
- 恶意软件、钓鱼链接、凭证窃取、垃圾广告和刷屏。
- 侵犯版权且没有合理使用依据的大段内容或资源。

技术板块允许安全研究讨论，但漏洞利用细节、有效凭证、未修复目标信息需按负责任披露规则处理。

### 14.2 处置原则

- 按内容和行为处置，不因观点本身进行不透明限流。
- 处置原因使用可理解的标准类别。
- 在法律允许时向内容作者展示状态和申诉入口。
- 高风险隐私泄露优先临时隐藏，再由管理员复核。
- 自动化只能辅助排序和初筛；永久删除、长期限制原则上由人工确认。

## 15. UI/UX 要求

### 15.1 视觉与布局

- 桌面端内容最大宽度建议 1200px；帖子正文阅读宽度 720–820px。
- 移动端底部提供主要发帖/回复入口，避免遮挡楼层锚点。
- 支持浅色、深色和跟随系统；颜色对比符合 WCAG 2.2 AA。
- 楼主、管理员、置顶、锁定、敏感、未读状态不能只依赖颜色区分。
- 长标题、超长 URL、中英文混排、代码块和大图不得破坏布局。

### 15.2 帖子详情关键组件

1. 面包屑与板块入口。
2. 标题、标签和状态徽标。
3. 主帖卡片：线程头像、楼主、时间、正文、媒体、投票、操作。
4. 阅读进度条和“继续阅读”提示。
5. 排序/仅看楼主开关；“仅看楼主”不改变原楼层号。
6. 楼层列表：楼层号、层主/楼主标记、引用、正文、投票、举报。
7. 粘性回复入口和编辑器。

### 15.3 编辑器

- 工具栏：粗体、斜体、引用、代码、链接、图片、剧透、表情包。
- Markdown 与预览双模式；粘贴图片前提示将移除元数据。
- 离开有未提交内容的页面时提示；P1 支持本机草稿。
- 显示字符数、图片数、标签数和限制。
- 提交中按钮禁用并展示进度，失败不清空输入。

### 15.4 空、错、慢状态

- 板块无帖子时提供发帖入口，不显示伪造内容。
- 搜索无结果时提供清除筛选建议。
- 接口错误保留输入并支持重试。
- 楼层分页加载展示骨架屏，避免布局跳动。
- 断网时明确提示；未确认写入不得伪装成功。

### 15.5 无障碍

- 所有功能可键盘操作，焦点顺序与视觉顺序一致。
- 弹窗有焦点锁定与返回；跳转楼层后移动焦点或通过实时区域提示。
- 图片要求替代文本，装饰性表情正确标记。
- 代码块、投票状态、公告级别对屏幕阅读器可理解。
- 尊重减少动态效果、系统字号和高对比设置。

## 16. 非功能需求

### 16.1 性能

- 核心页面移动端 LCP P75 < 2.5 秒，INP P75 < 200ms，CLS P75 < 0.1。
- 首页首屏压缩后 JS 预算建议 < 200 KB，编辑器和管理端按需加载。
- 图片使用响应式尺寸、现代格式和懒加载；首屏 Logo/主视觉除外。
- 列表 API P95 < 500ms，写操作 API P95 < 800ms，不含媒体异步处理。

### 16.2 可用性与恢复

- 月度可用性目标 99.9%。
- PostgreSQL/MySQL 生产模式启用自动备份和可用时的时间点恢复，目标 RPO ≤ 15 分钟、RTO ≤ 2 小时；SQLite 模式使用一致性在线备份或文件快照并包含 WAL，默认目标 RPO ≤ 24 小时、RTO ≤ 4 小时。三种模式均需定期恢复演练。
- 队列任务幂等、可重试、有死信队列。
- Redis 不作为唯一事实来源，丢失缓存不导致内容或投票永久丢失。

### 16.3 容量基线

PostgreSQL/MySQL 的 MVP 生产设计基线：月活 100,000、日活 20,000、峰值并发 1,000、每日新帖 10,000、每日回复 100,000、媒体存储月增 1 TB。容量达到 70% 时告警，并通过读副本、对象 CDN、异步计数和分区策略扩展。

SQLite 不承诺上述共享生产容量基线，默认定位为单实例、低并发部署。项目必须提供 SQLite 压测基线，并根据部署机器给出写入延迟和锁等待告警阈值；超过阈值时推荐迁移到 PostgreSQL 或 MySQL，而不是通过增加多个 SQLite 写实例横向扩容。

### 16.4 兼容性

- 支持最近两个主要版本的 Chrome、Edge、Firefox、Safari。
- iOS Safari 与 Android Chrome 为移动端重点验收环境。
- JavaScript 被禁用时至少可阅读公开帖子和公告；发帖等交互需明确提示启用脚本。

### 16.5 SEO

- 公开板块与帖子输出正确 metadata、canonical、Open Graph 和结构化数据。
- 搜索页、历史页、设置页、管理页和待审内容 `noindex`。
- 管理员可对板块或敏感帖子关闭索引。
- 删除或合并内容返回合适的 404/410/301，不永久保留软 404。

## 17. 分析指标与隐私约束

允许采集的事件仅用于产品质量和运营聚合，例如：页面类型访问、发帖成功/失败码、投票动作类型、继续阅读是否成功、举报处理耗时、Web Vitals。

禁止：

- 把事件与内部匿名账号 ID、原始 IP、完整 URL、帖子正文绑定。
- 构建跨板块兴趣画像或将历史用于广告。
- 使用能跨站识别用户的第三方分析 Cookie。
- 在事件属性中放入帖子标题、搜索词、恢复信息或用户输入。

事件至少达到配置的聚合阈值后才进入运营报表；低频敏感板块默认只显示总量趋势。

## 18. 测试与验收计划

### 18.1 单元与集成测试

- 匿名代号同帖稳定、跨帖不同，公开 DTO 不含内部用户 ID。
- 投票三态切换、唯一约束、并发与回滚。
- 楼层号并发分配无重复、无重排。
- 已读楼层单调合并、多设备竞争和被删锚点回退。
- 内容权限、板块状态、编辑时限和管理员作用域。
- Markdown 清理、危险 URL、XSS 与上传验证。
- 公告时间窗和站点设置回滚。
- 同一领域测试套件分别在 SQLite、PostgreSQL、MySQL 上运行，结果语义一致。
- 三种数据库上的迁移、字符集、时间精度、JSON 序列化、并发楼层号和唯一约束。

### 18.2 E2E 场景

1. 新访客自动获得匿名身份并完成发帖、回帖、投票。
2. 同一用户在同帖显示相同代号，在另一帖显示不同代号。
3. 两个用户并发回帖获得不同且连续的楼层号。
4. 用户阅读至 50 楼，另一设备恢复身份后从 50 楼续读。
5. 关闭云端历史后，服务端不再新增记录；清空后其他设备同步为空。
6. 管理员改名和 Logo 后前台正确刷新，旧设置可回滚。
7. 管理员锁帖后已打开页面提交回复失败并刷新为锁定状态。
8. 举报、隐藏、申诉/恢复和审计链完整。
9. 上传带 GPS EXIF 的图片后，公开文件不含 EXIF。
10. 普通用户无法通过修改请求访问他人历史、内容草稿或内部账号 ID。
11. 在 SQLite、PostgreSQL、MySQL 三种环境分别完成发帖、并发回帖、投票、搜索、历史同步和删除闭环。

### 18.3 安全测试

- OWASP Top 10、CSRF、XSS、SQL 注入、SSRF、IDOR、会话固定和权限提升。
- 上传压缩炸弹、畸形图片、双扩展名、SVG 脚本和恶意 GIF。
- 高频注册、发帖、投票、举报和恢复短语猜测。
- CDN/共享缓存中的个性化数据泄露测试。
- 日志、错误监控、分析事件和备份中敏感字段扫描。

### 18.4 上线阻断条件

- 公开 API 或页面泄露内部匿名账号 ID、IP、会话令牌或恢复明文。
- 跨账号读取浏览历史或编辑内容。
- XSS、权限提升、会话接管等高危漏洞未关闭。
- 楼层重复、投票可重复计数或已读进度大面积错乱。
- 删除/清空功能未实际进入清理流程。
- 无法执行数据库备份恢复或关键管理动作未审计。
- 任一受支持数据库无法从空库迁移、无法从上一版本升级，或核心行为与另外两种数据库不一致。

## 19. 交付阶段

### 阶段 0：产品与安全定稿（1 周）

- 确认匿名威胁模型、内容政策、数据保留和部署地区要求。
- 完成信息架构、关键页面线框、数据模型评审和安全评审。
- 确认数据访问层实现、三种数据库迁移策略、对象存储、队列、监控和部署平台。

### 阶段 1：工程基础（1–2 周）

- Next.js 工程、CI、环境配置、SQLite/PostgreSQL/MySQL 迁移矩阵、设计 Token。
- 匿名会话、管理员认证、权限框架、日志清理和测试框架。

### 阶段 2：论坛核心（2–3 周）

- 板块、帖子、回复、楼层、线程内代号、标签、投票。
- 首页、列表、详情、编辑器和响应式布局。

### 阶段 3：隐私与运营（2 周）

- 浏览历史、已读定位、头像、媒体、表情包、公告。
- 站点设置、举报、审核、审计、限流和内容安全。

### 阶段 4：质量与上线（1–2 周）

- E2E、安全、性能、无障碍、备份恢复和容量测试。
- 灰度发布、监控告警、运营手册和回滚演练。

预估为 2 名前端/全栈、1 名后端、1 名设计、1 名测试/安全兼职协作下的参考节奏；实际周期需根据媒体审核、合规地区和 UI 完整度重新估算。

## 20. 发布与运维

### 20.1 环境

- `local`：开发者本地，使用脱敏种子数据。
- `preview`：每个合并请求的临时环境，不接触生产数据。
- `staging`：接近生产配置，执行迁移和回归。
- `production`：最小权限、独立密钥、独立数据库和对象桶。

### 20.2 上线策略

- PostgreSQL/MySQL 数据库迁移采用向后兼容的扩展—迁移—收缩流程；SQLite 对不支持的表结构变更使用创建新表、复制校验、原子替换流程。
- 新功能使用服务端开关逐步放量，禁止把匿名身份或安全关键逻辑仅放客户端开关。
- 灰度观察错误率、写入失败、举报量、队列积压和 Web Vitals。
- 回滚不得丢失新产生的帖子、回复、投票或历史。

### 20.3 告警

关键告警包括：5xx 激增、鉴权失败异常、数据库连接耗尽、慢查询、队列积压、上传处理失败、内容举报突增、缓存命中骤降、磁盘/对象存储异常、备份失败和管理员异常批量操作。

## 21. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| “完全匿名”被误解为绝对不可追踪 | 用户信任和法律风险 | 产品页准确描述威胁边界，禁止使用无法兑现的营销表述 |
| 匿名环境导致垃圾、骚扰和违法内容 | 社区质量与运营风险 | 分层限流、风险挑战、举报、人工审核、紧急隐藏和审计 |
| 自定义头像造成跨帖身份关联 | 降低公开匿名性 | 默认使用线程头像，自定义全站展示需明确主动开启 |
| 用户在正文自曝身份 | 隐私泄露 | 编辑器提醒、隐私检测辅助、快速举报和优先下架流程 |
| 历史/断点与匿名目标冲突 | 数据关联风险 | 最小字段、可关闭、可清空、有限保留、仅本机模式 |
| 热点八卦涉及诽谤或隐私 | 法律与内容风险 | 板块规则、隐私举报优先级、证据保全边界、区域化合规评审 |
| 长帖断点定位不稳定 | 核心体验失败 | 稳定楼层 ID、游标定位、删帖回退、多设备单调合并测试 |
| CDN 缓存个性化数据 | 隐私泄露 | 公共和个性化响应拆分，正确 `Vary/Cache-Control`，上线前渗透测试 |
| 管理员滥权或账号被盗 | 内容与隐私风险 | 最小权限、MFA/Passkey、近期认证、审计和异常操作告警 |
| 三种数据库行为或迁移漂移 | 数据错误、版本无法升级 | 方言适配层、三库 CI 矩阵、schema checksum、跨库迁移校验 |

## 22. MVP 完成定义（Definition of Done）

MVP 只有同时满足以下条件才可对外发布：

- P0 功能均通过产品验收和自动化回归。
- SQLite、PostgreSQL、MySQL 均能从空库初始化、从上一版本升级，并通过相同核心业务测试。
- 匿名数据边界、隐私说明、社区规则和删除政策已上线。
- 普通用户无法在公开接口关联同一账号的跨帖身份。
- 浏览历史与已读续接在桌面端和移动端主流浏览器验证通过。
- 管理员可完成品牌、板块、标签、表情、公告和内容治理全流程。
- 高危安全问题为 0，中危问题有明确关闭计划且不涉及身份或内容泄露。
- 数据备份恢复、密钥轮换、紧急只读、内容下架和回滚完成演练。
- 监控、告警、值班联系人和事件响应流程可用。
- 无障碍达到 WCAG 2.2 AA 的核心路径要求。

## 23. 上线前必须确认的业务参数

以下不是功能缺口，但必须在部署前由产品、运营和合规负责人给出具体值：

1. 服务地区、适用法律、最低年龄与敏感内容政策。
2. 用户编辑时限、软删除时限、备份保留周期。
3. 单位时间发帖、回帖、投票、上传和恢复尝试额度。
4. 哪些板块允许被搜索引擎收录。
5. 自定义头像是否允许公开跨帖展示；建议默认不允许。
6. 自动内容检测供应商是否会接触正文，以及相应的数据处理协议。
7. 管理员层级、值班机制、举报 SLA 和申诉流程。
8. 站点正式名称、Logo、域名、默认主题和首批板块规则。

在这些参数未确认前，可以完成开发与测试，但不得宣称产品已满足特定地区的完整合规要求。
